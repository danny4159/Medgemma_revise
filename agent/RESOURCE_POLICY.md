# 연구 자원 사용 정책 — 사용자 의도 보완 (2026-09-24)

사용자의 목표는 RTX 3090 24GB 두 장으로 수행할 수 있는 중요한 의료 VLM 연구를 찾아,
가용 GPU를 적극 활용하여 방법론을 개발하고 충분한 실험으로 증명하는 것이다.
GPU를 쓰지 않는 연구나 가장 적은 연산만 쓰는 연구를 찾는 것이 아니다.
기존 연구 목표와 이력은 유지하고, 자원 사용에 대한 해석을 이 정책으로 보완한다.

## 자원과 권한

- 두 GPU 모두 사용이 허용되어 있다. 실행 직전 `nvidia-smi`로 실제 여유 메모리를 확인하고
  허용된 장치 중 여유가 큰 장치부터 쓴다. 다른 사용자의 프로세스는 종료하거나 변경하지 않는다.
- orchestrator의 `--gpus` 및 상속된 `CUDA_VISIBLE_DEVICES` 범위를 지킨다.
  자식 프로세스에 장치를 나눌 때는 허용 집합 안에서만 배정하고 논리 index와 물리 장치의 대응을 확인한다.
- MedGemma bf16 추론의 8~10GB는 참고값이다. 실제 작업의 peak를 측정하고 프로세스당 최소 2GB 여유를 둔다.
  학습에는 gradient·optimizer·activation 메모리가 추가되므로 추론 수치로 학습 가능 여부를 판단하지 않는다.
- 독립 데이터 shard, seed, baseline·ablation을 두 GPU에 병렬 배정한다. 한 장이 더 효율적이면
  그 근거를 기록한다. GPU 점유율 자체를 높이려고 불필요한 실험을 만들지 않는다.
- inference, training-free 방법, frozen feature/head 학습, 자원에 맞는 LoRA·adapter 등 경량 적응을
  함께 비교한다. 대규모 전체 모델 post-training의 부담을 모든 학습의 금지로 확대하지 않는다.
  실행 가능한 batch·정밀도·학습 범위는 작은 실측으로 판단한다.

## 실험 환경 구성 권한 — 2026-10-01 사용자 승인

- 합리적인 연구 실험·강한 비교군 실행에 필요한 패키지 설치, 버전 조정, venv/conda 환경 생성,
  의존성 빌드 및 공개 코드·접근 승인된 가중치 확보는 별도 사용자 승인 없이 수행할 수 있다.
  과거 문서·계획의 일괄 pip/conda 설치 금지는 이 규칙으로 대체한다. 미설치 자체를 과학적
  부적합이나 비교군 제외 근거로 쓰지 않는다. GPT 계획·리뷰는 read-only, 실제 구성은 Claude가 한다.
- 기존 `medgemma`와 orchestrator가 쓰는 환경, 다른 사용자의 환경은 제자리에서 변경하지 않는다.
  충돌 가능성이 있는 의존성은 `research/results/environments/<name>` 같은 git 제외 전용 경로에
  격리한다. 독립 환경의 생성·설치·수정은 자율적으로 진행하며 임시 셸 활성화에 의존하지 않는다.
  환경의 Python 절대경로, `conda run -p <env> ...`, 또는 해당 Python을 지정한 subprocess를 사용한다.
  `python -m pip`도 실제 대상 Python을 확인하고 사용한다. 기본 환경 변경이 꼭 필요하면
  실행 중 작업이 없음을 확인하고 복제 환경에서 먼저 검증한 뒤 영향·복구 방법을 별도 제안한다.
- 설치 전 디스크·Python/CUDA/PyTorch 호환성과 공식 의존성을 확인한다. 설치 후 import,
  GPU 가용성, 작은 실제 입력의 출력까지 검사한다. 환경 경로, 설치 명령, package/version 목록,
  코드·checkpoint 출처/revision, 실패·복구 내역을 결과에 보존하고 재현 설정은 연구 코드에 남긴다.
  checkpoint의 학습 데이터 중복·이용 조건도 확인한다. 설치 성공은 공정한 비교 검증과 다르다.
- 기존 `hf_cache/` 파일은 수정·삭제하지 않는다. 추가 모델·패키지 캐시는 별도 결과 경로를 쓴다.
  시스템/드라이버 변경·sudo, 다른 사용자 작업 변경, 데이터 권한 우회, 새로운 유료 자원,
  기존 자산의 파괴적 삭제는 이 승인에 포함하지 않는다. 필요한 경우 구체적 영향과 대안을 묻는다.
- 환경 문제로 막히면 확인한 오류, 격리 구성/호환 버전 등 시도, 남은 blocker와 해소 비용을
  남긴다. 같은 '설치 불가' 설명을 다음 반복으로 넘기지 않는다. 추가 권한이 실제 필요할 때만
  질문하며, 이미 승인된 격리 환경 설치를 재승인 대기로 돌리지 않는다.
- 실행 권한도 이 승인과 일치시킨다. 공식 자산 조회용 curl의 정해진 읽기 형식과
  `git ls-remote -- https://github.com/...`, `git hash-object -- <files>`를 허용한다.
  `--` 뒤 옵션은 해석하지 않도록 하며 객체 쓰기 `-w`는 허용하지 않는다. 공식 파일의
  다운로드·압축 해제·격리 설치는 승인된 Python 경로에서도 가능하다. 이는 네트워크 전체에
  대한 보안 격리나 Python의 임의 쓰기 허용을 뜻하지 않는다. 결과 경로·출처·보존 기준을 지킨다.

## 처리량 중심의 GPU 병렬 운영

- GPU당 worker 1개를 고정 상한으로 두지 않는다. 독립적인 요청·shard·seed·비교 실험이 남아 있고
  메모리가 허용하면 같은 GPU에 여러 프로세스를 배치한다. 두 GPU에 각 2개(총 4개 worker)도 후보이며,
  별도 사용자 승인 없이 현재 허용된 자원 안에서 선택할 수 있다. 연구 질문과 무관한 실험을 추가하지 않는다.
- 목표는 유효한 평가 요청/분 또는 학습 처리량을 높여 전체 완료 시간을 줄이는 것이다.
  VRAM을 채우거나 순간 GPU utilization을 100%로 만드는 것 자체를 목표로 삼지 않는다.
- 다음 본실험 전에 development/pilot 입력으로 현재 구성과 소규모 batch 확대 또는 GPU당 worker 2개를
  짧게 비교한다. 둘 모두를 불필요하게 전수 탐색하지 말고 유망한 구성부터 확인한다.
  전체 처리량, GPU별 peak VRAM, 긴 출력의 지연, 오류/OOM, CPU·RAM·I/O 경합을 기록한다.
  비교의 추가 비용이 예상 절약보다 크면 기존 실측을 재사용하고 이유를 적는다.
- 메모리 판단에는 모델뿐 아니라 KV cache·activation·batch·긴 출력 및 GPU 전체 실제 점유를 포함한다.
  동시 worker들의 예상 peak 합계와 다른 프로세스 점유에 worker당 최소 2GB 여유를 더해도
  GPU 용량 안에 들어야 한다. 시작 직전 다시 확인한다. 8~10GB 참고값만으로 자동 증설하지 않는다.
- 처리량이 좋아지고 출력·평가 조건이 유지되는 구성을 본실험에 적용한다. 안전한 추가 여유와
  남은 독립 작업이 있으면 더 높은 동시성도 검토한다. 느려지거나 OOM·경합이 생기면 동시성/배치를 낮춘다.
  GPU당 1개를 유지할 때는 메모리 부족, 실측상 이득 없음, 작업 의존성 등 구체적 근거를 남긴다.
- 실행기는 worker 수와 GPU 수를 분리해 같은 허용 GPU에 여러 worker를 매핑할 수 있게 한다.
  작업별 고유 ID·원자적 할당, worker별 결과 파일, 중복/누락 검사와 안전한 재개를 갖춘다.
  현재 실행 중인 큐의 claim을 지우거나 같은 출력 파일에 여러 프로세스가 임의로 쓰게 하지 않는다.
- 병렬화는 가설·표본·prompt·생성 길이·metric·성공 기준을 바꾸는 이유가 아니다.
  batch/worker 변경 시 결과 정합성·seed·출력 수를 점검하고 실행 구성을 기록한다.
  validation/test 결과를 보고 유리한 실행 구성을 고르지 않는다.
- GPT 계획은 비교할 병렬 구성과 선택 기준을 제시하고, Claude는 실측 후 배치를 확정한다.
  리뷰는 처리량·안전 여유·정합성 근거를 확인하되 utilization이 낮다는 이유만으로 유효한 연구 결과를 기각하지 않는다.

### 적용 시점 — 2026-09-24 사용자 요청

현재 iter_009에서 이미 실행 중인 실험은 중단·재시작하거나 worker를 추가하지 않고 기존 구성으로 마친다.
이 규칙은 다음 계획·리뷰와 후속 실험을 준비할 때 적용한다. 현 실험에 새 처리량 비교가 없다는 이유로
소급해 실패 처리하거나 같은 실험을 다시 실행하지 않는다. 실제 실행 장애에 대한 기존 복구 기준은 유지한다.

## 실행 규모와 중단 기준

- 1시간 초과 GPU 실행 금지와 근거 없는 45/55 device-minute 상한은 적용하지 않는다.
  가용 장비 안에서 목표에 필요한 수 시간의 실험도 진행할 수 있다. 시간만으로 재승인을 요구하지 않는다.
  사용자가 별도로 지정한 실행 deadline·timeout·GPU 범위는 지킨다.
- pilot은 입력·구현의 타당성, 메모리, 처리량을 확인하는 단계다. 타당성과 실행 가능성이 확인되면
  RESEARCH_POLICY.md의 가능성 탐색을 거쳐, 확대 기준을 충족할 때 사전에 정한 본실험으로 이어간다.
  동작 확인 통과만으로 최대 표본·모든 seed를 자동 실행하지 않으며, pilot 완료를 연구 완료로 간주하지 않는다.
  이 단계별 규모 규칙은 iter_011 이후 새 계획부터 적용하며, 실행 중인 iter_010의 계획은 유지한다.
- 계획에는 예상 wall-clock, GPU별 메모리와 병렬 배치, 본실험 규모, checkpoint·재개 방법,
  성공·실패·중단 조건을 적는다. 추정치와 실측치를 구분하고, 규모 변경은 실행 전에 이유를 남긴다.
  시간 예산이 필요하면 실측 처리량·필수 실험량·사용자 제한으로 산출하고 관행적인 작은 상한을 복사하지 않는다.
- 장시간 작업은 진행량·loss·실패·자원 사용을 기록하고 checkpoint를 남긴다.
  OOM, 비정상 수치, 진행 정체는 원인을 확인해 배치·동시 실행 수를 조정하거나 중단·재개한다.
- GPU 실험을 막는 데이터 누수·좌표 오류·잘못된 metric은 먼저 해결한다. CPU 전처리와 검증은
  필요한 만큼 수행하되 비핵심 코드 정비만으로 반복을 소비하지 않는다. CPU만 쓰는 반복에는
  실제 blocker, 이를 해소할 작업, GPU 실험으로 넘어갈 조건을 명시한다.
- 작은 pilot의 불확정 결과나 시간 부족을 접근법 전체의 실패로 일반화하지 않는다.
  추가로 식별력 있는 실험이 필요한지 판단하되, 유효한 반증이 있는 실패 실험을 무조건 확대하지 않는다.
- 추가 유료 자원, 현재 장비를 넘는 자원 확보, 접근 권한이 없는 데이터, 연구 목표 변경 등
  기존 허락 범위 밖의 결정은 사람에게 묻는다. GPT 계획·리뷰의 read-only 역할은 유지한다.

## 이전 계획을 재개할 때

- 과거 계획의 GPU 시간 상한은 당시 기록으로 보존한다. 사용자가 별도로 요구한 제한이 아닌
  에이전트의 임의 상한은 이 정책으로 대체하고, 기존 실행 코드의 budget 기본값·중단 조건도 확인한다.
- 완료된 실험·판정·결과 파일은 고치지 않는다. 미완료 작업부터 적용 내용을 보고서에 기록하고,
  이전 결과를 재사용할 때에는 입력과 설정이 유효한지 확인한다.
- 가설, split, metric, 비교군, 성공 기준을 결과에 맞춰 사후 변경하지 않는다.
  설계나 표본 확대가 필요하면 변경 근거를 별도 실험 계획으로 남기고 새 결과 경로를 사용한다.
