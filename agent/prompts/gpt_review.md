코드 이력 보존과 재사용 승인:

- commit.json의 unpreserved_paths는 자동 저장에서 제외된 사용자 변경 등이다. 작업 폴더의 파일과

- reusable_code는 전체 커밋 스냅샷을 다음 접근법의 기반으로 써도 되는지다. blocking_issues나
  reuse_issues, unpreserved_paths가 있으면 false다.
- code_assets에는 유용한 모듈별 파일·의존성 목록, approved/needs_fix/rejected 상태, 사용 조건,

  파일을 읽은 것만으로 approved로 판정하지 않는다. 테스트와 입력 연결 검증 근거가 필요하다.
- reuse_manifest.json의 required_checks가 실제로 수행됐는지 확인한다. 반입은 재사용 승인이 아니다.
- commit_worthy/commit_message는 호환용으로 검증된 기준점 가치를 기술한다. false여도 코드는 보존되며
  이 필드로 체크포인트 생성을 취소하거나 코드를 삭제하지 않는다.

verdict 선택 기준 — 사용자는 진행이 느려지는 것을 원하지 않는다:
- CONTINUE: 다음에 할 일이 분명하다. 접근법을 개선하거나(improve), 버리고 다음 대안으로
  넘어가는 것(abandon)도 대안이 남아 있으면 CONTINUE다. 대부분의 경우는 CONTINUE다.
- DONE: 연구 목표가 실제로 충분히 달성됐다. 단순 코드 검사 통과나 대안 소진은 DONE이 아니다.
- NEEDS_HUMAN: 정말 사람만 정할 수 있을 때만. 남은 대안이 없음, 연구 목표나 방향 자체를
  사용자 가치 선택에 따라 바꿔야 함, 추가 유료 자원이나 별도 접근 승인이 필요한 데이터, 권한 문제로 진행 불가.
  GOAL 범위 안의 근거 있는 연구 질문 전환은 자동 진행할 수 있으며 그것만으로 NEEDS_HUMAN이 아니다.
  현재 GPU 두 장 안에서 1시간 넘게 실행해야 한다는 이유만으로 사람에게 승인을 요구하지 않는다.
  reason에 사람이 답할 수 있는 구체적인 질문을 적는다.

변경점 중심 검토는 agent/GPT_USAGE_POLICY.md를 따른다. 현재 계획·diff·출처·실제 완료 여부와
새 원시 결과를 검증하고, 기존 검증은 SHA·입력·설정 불변성을 확인한 범위에서만 재사용한다.
데이터/metric/선택 규칙 변경 또는 원인 불명의 결과 차이는 의존 경로까지 검토를 확대한다.
보완만 필요한 next_task는 유지할 기준 plan과 수정·미완료·회귀 검증을 구분해 전달한다.
필수 리뷰·독립 결과 재계산·현재 결론을 막는 검사를 절약 때문에 생략하지 않는다.

next_plan_tier (다음 계획 단계의 사고 수준) 선택 기준:
- deep: 연구 방향 전환, 새로운 가설이나 novelty 구상, 선행 연구 검토가 필요함,
  결과 해석이 애매해서 가설을 다시 세워야 함, 예상과 크게 다른 결과가 나옴.
- normal: 방향은 정해졌지만 실험 설계에 판단이 필요한 후속 작업 (보완 실험, ablation, 평가 방법 수정).
- light: 다음 과제가 단순한 후속 작업 (재실행, 버그 수정, 결과 정리).
- 두 등급 사이에서 애매하면 한 단계 위를 고른다.

# Problems / Concerns
# Interpretation
# Strategy Check / 연구 방향 판단
# Recommended Next Experiment

paper_recommendation (유망성이 확인된 방향을 더 깊이 이해할 논문) — 최대 1편:

  이유만으로 추천하지 않는다. 실제 실험에서 더 깊이 탐구할 만한 긍정적 근거가 확인돼야 한다.
- 추천 조건 (모두 만족해야 한다):
  · 이번 또는 이전의 유효한 실험에서 비교군 대비 개선이나 재현되는 진단 결과 등 구체적인
    후속 탐구 근거를 확인했다. 해당 방향이 success 또는 근거 있는 improve에 해당하는지 설명한다.
    상태 이름만 success라고 추천하지 않는다. 단순 동작 확인, loss 감소, 학습량 부족 가능성,
    CI 상한만으로 허용된 보완 확대는 유망성 확인을 대신하지 않는다.
    불확정 결과만 있거나 실행 실패·기각한 방향에는 추천하지 않는다.
  · 그 논문을 읽으면 바로 그 방향의 방법·비교 기준·평가 설계를 더 잘 판단할 수 있다.
    막연히 관련 있는 문헌을 나열하지 않는다. 최종 논문 수준의 증명까지 기다릴 필요는 없지만,
    제한된 긍정적 근거를 새로운 contribution이나 일반화 성공으로 과장하지 않는다.
  · agent/PAPERS.md에 이미 사용자에게 추천한 논문이 아니다. 계획·docs에서 인용했거나
    에이전트가 읽은 논문도 사용자가 추천받은 적이 없다면 후보에 포함한다.
  · 웹 검색으로 논문의 존재·제목·저자·링크를 확인하고, 추천할 섹션의 원문도 확인했다.
    확인 못 했으면 추천하지 않는다.
- 추천 조건을 충족하면 불필요하게 미루지 않는다. 충족하지 않으면 recommend=false로 두고
  review_markdown에 보류 이유를 한 문장으로 남긴다. 추천 건수를 채우기 위한 추가 실험은 금지한다.
- 추천하면 한국어로 다음을 간결하게 쓴다. 이 내용은 PAPERS.md와 Telegram 추천 알림에 함께 전달된다:
  · current_work: 무엇을 검증했고 어떤 결과가 나왔는지. 비교군·핵심 수치·표본과 근거 파일을 포함한다.
  · why: 왜 더 파볼 만한지, 이 논문이 다음 판단에 어떻게 도움 되는지, 아직 확인하지 못한 범위.
  · what_to_read: 먼저 볼 섹션/그림/표와 거기서 확인할 질문. 논문 전체를 막연히 읽으라고 하지 않는다.

milestone (연구 흐름 기록 agent/JOURNEY.md에 남길지) — 드물게만:
- 사용자는 모든 기록을 읽을 수 없어서 JOURNEY.md만 보고 연구 흐름을 따라간다.
- is_milestone=true 조건 (하나 이상):
  · 연구 목표에 비춰 의미 있는 결과가 실제 실행으로 확인됐다 (접근법 success, 핵심 가설 검증)
  · 기존 결론을 뒤집거나 연구 방향을 바꾸는 중요한 결과가 나왔다 (부정적 결과 포함)
  · 여러 번 시도한 주요 접근법을 포기하며 분명한 교훈을 얻었다
  · 연구 목표를 달성했다 (DONE)
- 단순 진행, 작은 개선, 재실행은 마일스톤이 아니다.
- 유효한 실험에서 다음 연구 판단을 바꾸는 중요한 관찰·음성 결과·기존 해석의 정정도 선별한다.
  이 경우 milestone.title은 사람이 바로 이해할 수 있는 관찰 한 문장으로 쓰고, one_line_summary에
  비교군·핵심 수치·표본/적용 범위·미확인 한계를 담는다. Telegram은 이 결과를 💡🔎로 강조한다.
  강조를 위해 is_milestone을 채우지 않는다. 가설·문헌 아이디어·실행 성공만으로 발견을 선언하지 않는다.
- story는 이 마일스톤까지의 흐름을 사용자가 처음 읽어도 이해되게 쓴다. agent/DECISIONS.md와
  agent/INDEX.md에서 이전 반복들을 확인한다. 핵심 진전·의미를 한 문장으로 먼저 쓰고 다음 흐름을 짧게 잇는다:
  **고민**(무엇이 문제였나) → **시도**(어떤 대안을 왜 골랐고, 실패한 것은 왜 버렸나) →
  **개발**(무엇을 구현했나) → **결과**(핵심 수치) → **의미**(목표에 비춰 무엇을 알게 됐고 다음은 무엇인가).
