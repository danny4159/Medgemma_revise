# 연구 운영 기준

이 문서는 현재 사용자 의도를 반영한다. 과거 계획의 일률적인 포기·보존 규칙보다 우선한다.
연구 목표 자체는 `GOAL.md`를 따른다. 자원 사용은 `RESOURCE_POLICY.md`를 따른다.

## 연구 질문과 다음 투자 판단 — 2026-09-27 사용자 보완

의료 VLM·post-training이라는 큰 목표는 유지한다. 특정 데이터셋의 점수 개선, LoRA 사용,
기존 loss 이식, grounding·faithfulness라는 이름 자체를 새로운 contribution으로 간주하지 않는다.
RSNA와 기존 checkpoint는 연구 질문을 검증하는 자산이지 유지해야 할 연구 주제가 아니다.

### 전략 재검토가 필요한 시점

- 강한 단순 baseline 확보, 유효하지만 불확정인 결과의 반복, 연구 질문 변경, 새로운 대규모
  투자 직전에는 현재 방법의 개선 / 원인·능력 전이 진단 / 다른 연구 질문으로 전환을 비교한다.
  동일 문제 안에서 loss 이름만 바꾼 후보 목록으로 이 비교를 대신하지 않는다.
- 통상적인 버그 수정·계획된 평가·이미 승인한 확대 단계마다 재검토를 반복하지 않는다.
  직전 전략 판단이 여전히 유효하면 그 기록과 유지 이유만 짧게 인용한다. 별도 에이전트 호출이나
  고정 횟수의 문헌 조사·사람 승인을 추가하지 않고 기존 GPT 계획·리뷰 안에서 판단한다.
- GOAL 범위 안에서 근거에 따라 연구 질문을 바꾸는 것은 자동 진행할 수 있다. 사용자만 정할
  가치 선택, 목표 변경, 추가 권한이 필요할 때만 사람에게 묻는다.
- improve/success는 같은 접근법의 자동 연장 명령이 아니다. 실험이 성공해도 후속 투자는 보류할
  수 있고, 유효한 음성 결과도 중요한 경쟁 설명을 구분했다면 연구 진전일 수 있다.

### 계획·리뷰에 남길 판단

- 전략 재검토 시 plan_markdown의 `# Strategy Check / 연구 방향 판단`에 다음을 짧게 남긴다:
  (1) 중요한 사용 과제 또는 일반적 능력·원리, (2) 확인된 사실과 미확인 경쟁 설명,
  (3) 위 세 선택의 가치·정보 이득·비용 비교, (4) 선택 이유와 방향을 바꿀 조건.
  그 외 반복에서는 재검토 불필요 이유와 이전 판단의 출처만 적는다.
- 실험 전에 Evaluation에 양성 / 음성 / 불확정 결과 각각이 어떤 설명을 지지·약화하고
  다음 행동을 어떻게 바꾸는지 적는다. 모두 '다음 loss 시도'라면 왜 지금 필요한지 재검토한다.
  불확정이면 추가 표본·학습·검사가 정말 판단을 바꿀지와 보류 조건을 함께 정한다.
- contribution_path는 가장 가까운 기존 방법, 그 방법과 구별할 실패 조건·원리,
  필요한 비교 근거를 명시한다. 아직 모르면 미확인이라고 쓰고 이를 구분할 진단을 설계한다.
  탐색 전에 원인·신규성을 완전히 증명하도록 요구하거나 이미 새로운 기여라고 단정하지 않는다.
- review_markdown의 `# Strategy Check / 연구 방향 판단`에서 실행 유효성 / 성능 개선 /
  가설 지지 / 신규 기여 가능성을 각각 근거·미확인 범위와 함께 구분한다. 통계적 불확실성과
  관찰 범위를 유지한다. approach_status는 원 계획의 판정이며 다음 투자 결정과 혼동하지 않는다.
- goal_progress에는 위 구분을 요약하고, next_task에는 계속·진단·전환 중 권고와 이유·판단 조건을
  넣는다. 계획·리뷰의 한 줄 요약에도 방향상 중요한 미확인 사항을 남겨 기록·Telegram에서 보이게 한다.
  기존 JSON 필드·enum을 사용하고 새 판정 체계나 필수 모델 호출을 추가하지 않는다.
- 구현·평가의 정확성과 과학적 질문의 가치를 별도로 검토한다. 현재 결론·실제 재사용 경로에
  필요한 수정을 우선하고, 주변 코드 정비로 과학적 질문을 계속 미루지 않는다.

### VLM의 가치와 능력 전이를 확인할 때

- 내부 위치 학습을 택했다면 실제 과제에서 강한 직접 SFT와 detector+VLM 또는 적절한
  encoder+head 같은 모듈형 대안을 검토한다. 원본 영상·영역 정보·필요한 도구 사용을 막아
  약한 비교군을 만들지 않는다. 데이터·학습량·입력·추론 비용의 차이를 명시한다.
- 모든 검출기를 이기거나 모듈형 구성으로 불가능한 기능을 만들 필요는 없다. 일반화,
  데이터 효율, 근거–답변 일치, 계산 비용 등 목적에 맞는 이점을 실제 비교로 확인한다.
  localization 자체의 일반적 학습 원리·효율 개선도 후보이며 QA·보고서 전이를 무조건 강제하지 않는다.
- 전이 진단에서는 좌표 출력 / 의미가 달라진 질문에 대한 영역 선택 / 근거를 활용한 판단을
  구분한다. 프롬프트 표현 변경을 대상 변경으로, JSON 형식 적응을 시각 능력 변화로 오해하지 않는다.
  평가 prompt·parser와 필요한 형식 보정은 개발 자료에서 정하고 동일 조건으로 비교한다.
- bbox에서 만든 개수·위치 QA에는 검출+규칙 baseline을 검토하며 이를 임상 reasoning의 증명으로
  삼지 않는다. 정답 box를 제공하는 oracle 조건은 원인 분리용이며 실용 비교군과 분리한다.
  bbox 제거·crop만으로 '임상적으로 정상'을 정답으로 만들지 않는다. 정답이 보장되는 범위만 평가한다.
- 새 학습 전에 기존 base·SFT·추가 SFT 및 평가 코드를 활용할 진단을 우선 검토한다.
  큰 benchmark를 먼저 만들지 말고 다음 선택을 구분할 최소 범위로 시작한다. 이후 확대는
  효과·불확실성·중요성에 맞춰 충분히 하며, 모델 계열·원천 데이터 중복과 누수를 확인한다.

### 현재 실험과의 적용 경계

- iter_014는 원래 계획한 구현·학습·조건부 후속 비교·평가를 유지한다. 이 보완 때문에 중단,
  재학습, 기준 변경을 하지 않으며, 새 요구를 소급해 실행 실패나 가설 기각으로 판정하지 않는다.
- iter_014 리뷰는 원 계획의 성과와 다음 투자 가치를 분리한다. 다음 계획은 연구 방향 재검토를
  우선 과제로 전달한다. next_plan_tier는 GPT_USAGE_POLICY의 deep_medium/deep_high 기준으로
  선택하며 전략 재검토라는 이름만으로 high를 강제하지 않는다. 새 전략이 미확정인 동안 후속 loss 탐색을
  이미 결정된 다음 과제로 쓰지 않는다.
- iter_014 이후 첫 새 계획에서 위 전략 비교를 수행한다. 기존 checkpoint의 능력 전이·원인
  진단을 우선 후보로 검토하되, 더 가치 있는 후보가 있으면 근거로 선택한다. faithfulness나
  특정 진단을 새 최종 목표로 고정하지 않는다. 이 첫 판단은 기록에 남기고 매 반복 재시작하지 않는다.
- 기존 결과·checkpoint·코드·음성 결과를 보존하며 GOAL과 과거 계획·리뷰를 덮어쓰지 않는다.
  이 지시는 다음 호출부터 전달된다. 현재 세션에 즉시 새 실험을 끼워 넣거나 RESUME.md로
  진행 중인 반복을 superseded 처리하는 지시가 아니다.

## 목표에 연결되는 실험

### 진단에서 최소 방법 실험으로의 전환 — 2026-09-30 보완

- 실행 중인 iter_039는 원래 가설·표본·확대 기준·검증·종료 조건을 유지한다. 이 보완은
  현재 실험을 중단하거나 판정 기준을 소급 변경하지 않는다. 다음 리뷰에서는 원 계획을 평가하고
  다음 투자 판단에만 보완을 적용한다. GOAL·과거 결과·체크포인트를 바꾸거나 replan하지 않는다.
- 관찰 탐색 → 최소 방법 실험 → 본격 확대 → 논문 기여 입증을 구분한다. 작은 방법을 시험하기
  전에 내부 원인·다른 모델 일반화·신규성의 최종 증명을 모두 요구하지 않는다. 반대로 pilot을
  통과했다고 검증된 해법이나 새로운 contribution으로 선언하지 않는다.
- `experiment_role=method, method_stage=pilot`은 실제 사용 조건의 중요한 문제, 단순 대안의
  구체적인 부족함, 가장 가까운 방법과의 관계, 경쟁 설명을 구분할 최소 변경이 있을 때 선택한다.
  이전 full review에서 valid_experiment=true이고 blocking_issues가 없으며 evidence·usage_checks가
  있는 현재 목표의 observed/validated 한계를 연결한다. candidate·문헌 아이디어·CPU 준비만으로
  시작하지 않는다. 이는 독립 재현 완료 전에도 허용되는 명시적 방법 실험이지 diagnostic 우회가 아니다.
- `method_stage=full`인 method와 confirmatory는 기존 validated 기준을 유지한다. pilot에서 full로
  자동 확대하지 않는다. pilot 효과·불확실성·강한 baseline·실제 비용을 리뷰하고 별도 계획을 세운다.
  setup/diagnostic은 method_stage=none이며 기존 plan에 새 필드를 소급해서 요구하지 않는다.
- 새 계획의 `decision_contract`에는 경쟁 설명/개입 대조, 양성·음성·불확정의 다음 행동,
  표본·후보·학습 또는 요청량과 근거 있는 비용, 종료 결정을 적는다. method에서는 모든 항목을
  구체화한다. 연구 질문·baseline_plan·contribution_path와 연결하고 반복 서술 대신 원문을 참조한다.
  모든 결과가 '다른 진단 추가'이면 계획을 수정한다. 불확정의 후속 검사는 결정을 바꿀 미해결
  요인과 정밀도/정보 이득이 있을 때만 정하고, 허용한 보완 후에도 미해결이면 보류/전환 또는
  새 근거가 있는 한정 후속 중 하나를 선택한다. 횟수만으로 자동 기각하지 않는다.
- 진단의 종료 결정은 최소 방법 시험 / 근거 있는 한정 보완 / 투자 보류·전환 중 하나다.
  가장 가까운 기존 방법, 실제로 구별할 주장, 현재 증거와 빠진 증거를 Strategy Check에 남긴다.
  단순 해결책이 있으면 무조건 포기하지 말고 정확도·latency·GPU 시간·annotation budget 중
  사용 목적에 중요한 지표와 최소 가치 있는 개선 폭을 사전에 정한다. 같은 비용의 정확도 또는
  같은 정확도의 비용 개선도 가치다. 모든 실험에 F1 0.10 같은 고정 문턱을 복사하지 않는다.
- `research_track`은 approach/git branch와 별개인 큰 연구 질문의 안정된 id다. 데이터·프롬프트·
  구현 변경만으로 이력을 초기화하지 않는다. `related_iterations`로 과거 관련 진단·실패·사용자
  전환까지 연결한다. 기존 기록을 다시 쓰지 않고, 자동 집계가 모르는 의미상 연관은 GPT가 원문으로 판단한다.
- 기존 계획·리뷰 안에서 track의 해결된 질문 / 남은 핵심 불확실성 / 다음 결정을 바꿀 증거를
  갱신한다. 진단·setup·실행 복구에 소모한 반복과 누적 비용을 함께 보되 유효 실험 수와 혼동하지
  않는다. 전략 전환·진단 연장·큰 투자 때 판단하고 매 batch마다 별도 조사·사람 승인·모델 호출을 만들지 않는다.
- 기계 gate는 필드·근거 상태·현재 목표·이전 리뷰의 무결성만 검사한다. 문장만 채웠다고 가치·신규성·
  대조군 공정성을 승인하지 않는다. GPT 리뷰는 contract의 실제 충족 여부와 다음 투자를 독립 판단한다.

- `LIMITATIONS.md`와 해당 원본 리뷰를 먼저 읽는다. 주장 상태는 candidate(후보), observed(제한된 관찰),
  validated(사용·평가 오류를 통제한 재현), rejected(주장 기각/정정)로 구분한다.
- 방법 개발 전에 정상 사용 조건에서도 남는 성능 문제를 실제 출력으로 확인한다. 공식 사용법의
  출처·버전, chat template, 전처리·좌표, 충분한 출력 길이, parser, 정답·metric을 대조하고,
  합리적인 prompt 변경으로 해소되는 문제와 내용상 오류를 분리한다.
- 모델 내부 원인의 완전한 증명은 방법 개발의 필수조건이 아니다. 다만 문제의 적용 범위·빈도·크기,
  단순 baseline, 독립 평가 근거와 해결책의 연결이 필요하다. head/proxy의 실패를 실제 모델 출력의
  결함으로 간주하지 않는다. probe 점수와 생성 bbox 점수를 서로 다른 지표인 채 직접 비교하지 않는다.
- method full/confirmatory 계획은 현재 목표에서 validated인 `limitation_ids`를 지정해야 한다.
  method pilot은 위의 제한된 observed 근거 경로를 사용하며 orchestrator는 두 경로 모두 --auto에서도 검사한다.
  이를 피하려고 방법 개발을 diagnostic으로 이름만 바꾸지 않는다.
  diagnostic은 실패 현상·원인 후보를 구분하는 실험이고, CPU 준비만으로 validated로 승격할 수 없다.
- 공식 사용법을 수정해 문제가 사라지면 주장을 정정하고 다른 후보를 탐색한다. 문제는 남지만
  해결책 연결이 약하면 후보를 다시 선정한다. 결론 불충분이면 의사결정을 바꾸는 검증만 추가한다.

- 계획은 `research_question`, `experiment_role`(setup/diagnostic/method/confirmatory),

## 단계별 표본·학습·평가 규모

적용 시점: 2026-09-24 사용자 지정에 따라 다음 실험 계획(iter_011 이후)부터 적용한다.

현재 반복 안의 후속 학습/평가를 축소하지 않는다. 리뷰도 새 기준을 소급해 실패 사유로 삼지 않는다.

전체 데이터·최대 학습량·여러 seed를 모든 후보에 처음부터 적용하지 않는다.
현재 의사결정을 바꿀 수 있는 규모로 시작해 근거에 따라 확대한다. GPU 회피나 영구적인 작은 pilot 반복을 뜻하지 않는다.

1. 동작 확인: 작은 train 표본으로 입력·정답·mask·gradient·출력·메모리·재개를 검사한다.
   overfit 성공은 학습 경로가 작동한다는 뜻이지 일반화 개선의 근거가 아니다.
2. 가능성 탐색: 대표성 있게 고정한 train/validation 일부와 우선 1개 seed로 실제 생성 개선,
   학습 추세·변동·실패 유형·처리량을 확인한다. 희귀·어려운 유형을 편의상 제외하지 않는다.
3. 규모 확대: 탐색 근거로 유망성이 있거나 표본·수렴 부족을 해결하면 판단이 가능할 때
   필요한 학습량·validation·비교군·seed로 확대한다. 근거가 충분하면 탐색을 생략하고 그 이유를 적을 수 있다.
4. 독립 확인: 설정·checkpoint 선택을 마친 뒤 보존한 확인 집단에서 비교한다.
   논문 수준의 주장은 필요한 정밀도·seed 재현성·추가 데이터셋 근거를 갖춘다. 데이터셋 전체 사용 자체가 필수는 아니다.

- GPT 계획은 각 단계의 질문, 표본/환자/요청 수, 추출·층화·중복 방지, 학습량·seed,
  평가 빈도, 예상 비용, 확대/보완/보류/기각 기준을 기존 Proposed Experiment와 Success Criteria에 명시한다.
  예시 표본 수를 일률적인 상한으로 복사하지 않는다. 규모는 효과 크기·정밀도·변동성과 실측 처리량에 맞춘다.
- 작은 동작 확인을 통과했다는 이유만으로 모든 학습률×여러 seed×전체 epoch 평가를 자동 시작하지 않는다.
  가능성 탐색에서 실제 GPU 실험·출력 평가를 하고, 미리 정한 기준에 따라 다음 단계로 넘어간다.
  조건이 명확하면 같은 Claude 호출 안에서 진행할 수 있다. 단계마다 새 GPT 호출·사람 승인을 강제하지 않는다.
- 매 epoch 전체 validation 생성은 기본값이 아니다. 고정된 층화 validation 일부로 추세를 확인하고,
  사전에 정한 milestone/후보 checkpoint에서 전체 validation을 사용하는 방식을 우선 검토한다.
  전체 평가가 매번 필요한 경우 이유·비용을 적는다. 최종 후보는 같은 검증 범위로 비교한다.
- loss만으로 실제 생성 개선을 판단하지 않는다. 일부 validation의 잡음 때문에 유망한 후보를 조기 폐기하지 않는다.
  작은 표본의 무개선은 구현 오류·학습 부족·정밀도 부족과 구분한다. 짧은 학습의 실패를 전체 방법의 실패로 확대하지 않는다.
- split·층화·seed·평가 일정·확대 기준은 결과를 보기 전에 고정하고 manifest/config로 보존한다.
  탐색용 subset은 독립 test가 아니라 개발 자료다. test를 반복 확인하거나 유리한 표본·seed만 선택하지 않는다.
  확인 집단의 성능을 본 뒤 조건을 변경하면 해당 집단을 개발 자료로 전환하고 새로운 독립 확인 근거를 마련한다.
- 결과 보고에는 현재 도달 단계, 계획 대비 실제 사용량, 확대/보류 이유, 아직 하지 않은 독립 검증을 구분한다.
  필요한 본실험은 충분히 실행하되 더 작은 단계로 판단 가능한 후보에 처음부터 큰 비용을 쓰지 않는다.

## 가설 판정과 코드 보존은 별개

- 공통 관리 코드·정책·프롬프트·테스트는 상위 저장소 main에서 관리하며 연구 접근법의 성공 여부와
  독립적으로 유지한다. research/ 브랜치 전환·복귀로 공통 정책을 되돌리거나 실험과 함께 폐기하지 않는다.
  실험 고유 설정·판정은 해당 연구 코드·iter 기록에 남긴다. 공통 개선은 실패한 접근법에서 나와도
  검토·테스트 후 별도 관리 커밋으로 보존한다. 정책 자체의 결함 수정은 별도의 명시적 변경으로 한다.
- 상위 관리 기능 브랜치는 필요할 때 별도 worktree에서 사용하고 검증 후 main에 반영한다.
  실행 중인 상위 작업 폴더의 브랜치는 바꾸지 않는다. 연구 기록 자동 커밋과 관리 변경 커밋을 분리하고,
  관리 변경 완료 시 선별 커밋한다. push는 사용자가 허용한 원격·범위에서 수행하며 원격 미설정인
  research/ 코드나 Git 제외 결과까지 상위 저장소 push로 백업됐다고 보고하지 않는다.
- 구현 종료·안전한 중단 시 이번 작업의 소스 변경은 성공/실패·리뷰 여부와 무관하게 체크포인트
  커밋으로 보존한다. 커밋은 개발 이력이지 성공 인증이 아니다. Claude는 구현하고 orchestrator가 커밋한다.
- `commit_worthy`는 과거 형식 호환용 기준점 평가이며 저장을 막지 않는다. `reusable_code`는 전체
  스냅샷의 재사용 승인, `code_assets`는 파일·모듈별 승인/수정 필요/기각과 실제 검증 근거다.
  전체 실험이 실패해도 올바른 로더·평가기 등은 모듈 단위로 재사용할 수 있다.
- 실행 전 `code_baseline.json`으로 범위를 고정한다. 기존 사용자 변경·외부 staged 변경은 자동 커밋하지 않는다.
  모델·데이터·결과·5MB 초과 파일·symlink·비밀정보 의심 파일은 제외하고 사유를 기록한다.
  비밀정보 패턴 검사는 완전한 보안 검사가 아니다. 코드에 비밀정보를 넣지 않는다.
- 체크포인트는 `checkpoints/`, `checkpoint.json`과 영구 ref에 보존한다. 최종 리뷰 대상은 `commit.json`과
  `iter_NNN` 태그에 연결한다. `changes.patch`는 구현 전 SHA→리뷰 대상 SHA 비교다.
  `code_review.json`은 검증 결과를 해당 SHA에 연결한다. 브랜치·태그·이력은 자동 삭제하지 않는다.
- stash는 이전 버전의 미커밋 작업·소유 범위가 불명확한 변경 등 예외 상황의 안전망이다.
  전환 시 stash·영구 ref·patch로 보관하고 `CODE_ASSETS.md`에 출처를 남긴다.
  자동 저장 제외 파일이 남아 있으면 stash에 우회 저장하지 않고 전환을 보류한다. 원본은 유지한다.
  results/ 등 제외 산출물은 별도 파일로 유지한다. 로컬 Git 커밋은 외부 백업이나 원격 push가 아니다.
- 새 접근법은 최근 재사용 승인 커밋을 기반으로 한다. 특정 승인본이 필요하면 계획의
  `reuse_iteration`으로 선택한다(0은 자동). 같은/기존 브랜치를 잇는 경우에는 그 브랜치를 유지한다.
  일부 모듈만 쓸 때는 계획의 `reuse_assets`에 전체 commit SHA·개별 파일 경로·의존 파일·이유·
  required_checks를 명시한다. orchestrator가 실제 blob을 확인하고 Claude 실행 전에 선별 반입한다.
  원본 누락·경로 이탈·symlink·기존 파일 충돌이면 시작을 보류한다. 임의로 덮어쓰거나 재구현하지 않는다.
  이미 복구된 동일 내용 파일은 명시적 manifest로 이번 작업에 편입할 수 있다.
  반입 후 Claude는 관련 테스트·입력 연결을 실제 검증하고 GPT가 승인 범위를 판정한다.
  manifest가 없는 기존 계획은 자동 반입하지 않는다. 필요한 파일을 지정해 재계획한다.
- 결함 있는 보관본을 그대로 신뢰하지 않는다. `reuse_issues`를 해결하고 현재 입력과 provenance를
  확인한 뒤 재사용한다. 성공한 코드·유효한 음성 결과·원본 기록을 지우거나 덮어쓰지 않는다.

## 검증과 방향 전환

- success: 계획한 기준 충족. improve: 구체적인 개선 근거 있음.
  inconclusive: 표본·정밀도·수렴 등으로 결론 불충분.
  execution_failed: 실행·데이터·환경 오류로 유효한 검증을 못 함.
  abandon: 유효한 근거와 기회비용을 검토해 특정 설계에 대한 투자를 중단함.
- `valid_experiment=true`는 계획의 가설을 해석 가능한 방식으로 실제 검증했을 때만 쓴다.
  준비·코드 검사만 했거나 실행 무효면 false다. 유효한 실험도 정밀도가 낮으면 inconclusive일 수 있다.
  과거 미분류 결과를 자동으로 실패/유효 실험으로 재해석하지 않는다.
- `failure_scope`에 실패/불확정이 적용되는 데이터·설계·학습 조건을 적는다.
  작은 head 실패를 전체 표현·anatomy·경량 학습 가능성의 실패로 일반화하지 않는다.
- 리뷰 문제는 `blocking_issues`(현재 결론 무효), `reuse_issues`(재사용 전에 수정),
  `deferred_issues`(추후 견고성 개선)로 나눈다. 선택적 보완 때문에 유효한 실험 전체를 실패 처리하지 않는다.
  `goal_progress`에는 목표에 관해 새로 알게 된 것과 아직 검증하지 못한 것을 쓴다.
- `--max-attempts`는 유효한 실험 누적 후 재평가 기준이지 자동 포기 횟수가 아니다.
  계속하거나 기각한 설계를 다시 시도하면 `continuation_reason`에 이전 기각 범위, 새 근거,
  기대 정보 이득과 중단 기준을 쓴다. 인프라 수정/실행 실패를 이 횟수에 넣지 않는다.
- DONE은 목표의 실제 충족 근거가 있을 때만 사용한다. 대안이 소진됐거나 목표를 바꿔야 한다면
  완료로 포장하지 말고 NEEDS_HUMAN으로 판단을 요청한다.

## 중단 후 사용자 보완

- 사용자 보완 지시는 이전 계획보다 우선하되 목표·권한 범위를 임의로 넓히지 않는다.
  agent/RESUME.md 또는 --replan으로 전달하면 기존 미완료 반복은 superseded로 보존하고 새 반복에서
  GPT가 재계획한다. 실패·완료 판정을 조작하지 않는다. Claude는 새 세션으로 시작한다.
- GPT는 이전 계획·부분 결과·보존 코드·한계 기록을 읽고 무엇을 유지/보류/변경했는지 명시한다.
  단순 중단이며 보완 지시가 없으면 기존 단계·세션부터 이어간다.
- 조사 라운드의 research_notes와 open_questions를 다음 라운드에 전달한다. 기존에 확인한 사실을
  다시 미확인으로 적을 때는 이전 출처·버전과 대조해 불일치 이유를 설명한다.
