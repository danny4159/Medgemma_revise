# 사람이 읽는 기록·알림의 작성 기준

적용 대상: 계획 설명, 조사 노트, 구현 보고서, 리뷰, INDEX/DECISIONS/JOURNEY, 논문 추천, Telegram, 사용자 답변.
표현을 쉽게 만드는 기준이지 구현·연구·검증을 단순화하라는 지시가 아니다.

## 기본 순서

1. 핵심: 무엇을 하려는지 / 무엇이 확인됐는지 한두 문장으로 먼저 쓴다.
2. 근거: 판단에 필요한 수치·비교·출처를 제시한다.
3. 의미와 한계: 목표에 어떤 진전인지, 아직 무엇을 말할 수 없는지 구분한다.
4. 다음: 다음 작업과 이유, 사용자 결정이 필요한지 적는다.

- 짧은 문장에 한 가지 요점을 담는다. 장황한 작업 나열·반복 설명·전문용어 연결을 피한다.
- metric·모델명·기술 용어는 유지한다. 익숙하지 않을 용어는 처음에 짧게 뜻을 덧붙인다.
  예: data leakage(평가 정보가 학습·선택에 섞이는 문제), ablation(구성요소별 효과 비교).
- 숫자는 비교 대상·단위·표본 수와 함께 쓴다. 관찰, 해석, 추정을 구분하고 미실행·미검증을 명시한다.
- 코드 작성 완료, 테스트 통과, 유효한 실험, 가설 지지, 연구 목표 달성을 같은 ‘성공’으로 묶지 않는다.
- 제목·짧은 문단·목록으로 나누되 섹션을 불필요하게 늘리지 않는다. 표는 실제 비교가 쉬워질 때만 쓴다.
  Markdown 제목 뒤와 목록 앞에는 빈 줄을 둔다. 경로·명령·정확한 수치와 원문 링크는 유지한다.

## 요약과 상세의 분리

- 완성된 계획·구현 보고서·리뷰는 맨 앞에 ‘요약’을 둔다. 핵심/근거/주의/다음을 3~5개 짧은 항목으로 적는다.
  계획은 예정과 판단 기준, 구현은 실제 실행 결과, 리뷰는 판정과 근거를 중심으로 쓴다.
- 상세에는 기존 필수 섹션, 재현 명령·설정·파일·오류·검증 근거를 빠짐없이 남긴다.
  간결함을 이유로 필수 정보나 부정적 결과를 버리지 않는다. 원본 기록은 소급해서 다시 쓰지 않는다.
- 한 줄 요약(plan_summary, SUMMARY, one_line_summary)은 ‘무엇을 했고/할 것이며 무엇이 달라졌는지’가 드러나게 쓴다.
  보통 1~2문장으로 작성하고, 판단을 뒤집을 수 있는 조건·미검증 범위는 요약에도 남긴다.
- 조사 중에는 전체 계획 대신 ‘새로 확인한 것 / 의미 / 남은 질문과 필요한 확인’을 기록한다.
  research_notes의 근거·대안 비교·불확실성을 길이 제한으로 잘라내지 않는다.

## Telegram

- 알림은 개별 작업 나열이 아니라 같은 연구의 연속 기록으로 쓴다. 제목은 `iter_NNN | 현재 단계·핵심 변화`로
  두고 계획 검토 → 계획 확정/실행 준비 → 결과 검증 → 결과/후속 제안을 구분한다. 계획을 승인했다고
  GPU 학습이 시작됐다고 표현하지 않는다. 리뷰의 후속 제안도 이미 실행 중인 작업처럼 쓰지 않는다.
- 각 알림에 짧은 연구 이름과 데이터의 영상 종류를 반복해 앞 알림을 찾지 않아도 이해하게 한다.
  데이터·모델·과제·가설이 바뀌면 `이전 → 현재`와 바꾼 이유를 눈에 띄게 표시한다.
  바뀌지 않은 연구의 코드 복구는 `같은 질문 유지 · 실행 복구`로 쓰며 새 방향/새 발견처럼 알리지 않는다.
- 질문은 실제 입출력으로 설명한다. 예: `디스크 일부 위치에서 배운 손상 등급 판독이 다른 위치에서도 되는가?`.
  `annotation`은 정답표/사람이 표시한 영역 등 실제 의미로, `QA`는 영상에 대한 질문·정답으로 쓴다.
  `UCSF-PDGM-VQA`만 쓰지 말고 `뇌종양 MRI 질문·정답 자료(UCSF-PDGM-VQA)`처럼 역할을 먼저 설명한다.
  의미를 모르는 약어를 추측해서 풀지 않는다. 비교군 F/R/C/H, T24/E24, gate, oracle 등의 내부 표기는
  사람용 요약에서 전체 영상/대상 부위/일반 분류기, 학습 24명, 실행 전 검사, 정답 위치 제공 등으로 설명한다.
- 실패 알림에는 실제 완료된 것과 막힌 것을 나누고, 실행 실패와 가설의 부정적 결과를 구분한다.
  후속은 `무엇을 해서 어떤 판단을 내릴지`를 한 문장으로 쓴다. `할 일`, `다음`, `정합성 확인` 같은
  추상적 항목만 나열하지 않는다. 유효한 중요한 관찰은 기존 💡🔎 기준으로 강조한다.
- 별도 요약 모델 호출은 추가하지 않는다. 아래 사람용 Markdown 블록을 기존 계획/리뷰 호출에서 함께
  작성한다. 이 블록은 알림 표시 전용이며 누락돼도 기존 요약으로 표시한다. schema·진입 판정·학습 조건에는
  사용하지 않는다. 과거 기록을 소급 수정하지 않는다.

### 계획의 알림 맥락

`plan_markdown`의 요약 바로 뒤에 아래 블록을 쓴다. 각 항목은 한 줄이며 빈칸/미정은 솔직히 표시한다.
연구 이름·데이터·모델·과제·가설 문구는 의미가 유지되면 직전 표기를 그대로 재사용한다. 단순 문구 변경을
방향 전환처럼 표시하지 않는다. `연결`에는 직전 결과 → 유지/변경 이유를 적고, 데이터가 바뀌면 이전과
현재를 모두 적는다. `질문`과 `가설`은 검증 전의 예상이지 확인된 결과가 아니다.

```markdown
## 알림 맥락
- 연구: 짧고 안정된 연구 이름
- 데이터: 영상 종류와 데이터셋 이름
- 모델: 모델 이름과 학습 여부
- 과제: 입력을 받아 무엇을 출력하는가
- 가설: 이번에 확인할 예상 또는 경쟁 설명
- 질문: 사용자가 이해할 핵심 질문 한 문장
- 변경: 이어감 / 구체화 / 방향 전환 / 실행 복구 중 해당하는 하나
- 연결: 직전 반복에서 무엇을 확인했고 왜 이번 작업으로 이어지는가
- 작업: 이번 반복에서 실제로 할 작업과 그 작업으로 내릴 판단
```

### 리뷰의 알림 요약

`review_markdown`의 요약 바로 뒤에 아래 블록을 쓴다. 핵심 수치·비교 대상·미확인 한계를 보존한다.
실행 미완료이면 `결과`에는 어디까지 했고 왜 막혔는지, `의미`에는 가설은 아직 판단 못 했음을 적는다.
`후속`은 실행 확정이 아니라 다음 계획에 대한 권고다. 반드시 review의 판정·next_task와 일치시킨다.

```markdown
## 알림 요약
- 결과: 이번에 실제로 확인한 것 또는 실행을 막은 문제
- 의미: 연구 질문에 무엇을 알게 됐고 무엇은 아직 모르는가
- 후속: 어떤 작업으로 남은 어떤 판단을 할 것을 제안하는가
```

### 길이와 강조

- 일반 알림은 모바일 한 화면에서 읽도록 제목 → 핵심 1~2문장 → 중요한 한계 1문장 → 다음 행동
  1문장으로 쓴다. 보통 본문 3~6줄이며 전체 상세 설명이나 실행 과정을 옮기지 않는다.
- plan_summary와 one_line_summary는 쉽게 읽히는 1~2문장(가급적 180자 내외)으로 핵심 질문/결과와
  결론을 바꿀 제한을 함께 담는다. 원인·숫자·비교군을 모두 삭제한 막연한 '잘 진행 중'은 피한다.
  next_task의 첫 문장은 다음 행동과 이유만 명료하게 쓰고 구현 체크리스트·분기 상세는 뒤에 둔다.
  이 길이 기준은 사람용 요약에만 적용하며 상세 연구 노트·실험 계획·검증 근거를 제한하지 않는다.
- 단순 작업 완료는 🧪, 대기는 ⏳, 오류는 ❌, 사용자 결정은 🙋로 구분한다. 실제 실험을 리뷰해
  연구 판단을 바꾸는 결과·관찰을 발견했으면 💡🔎 '중요한 결과·관찰'로 눈에 띄게 표시한다.
  의미 있는 음성 결과나 기존 해석의 정정도 포함하되, 성공 판정만으로 자동 강조하지 않는다.
- 중요한 관찰은 기존 milestone 기준으로 선별한다. 가설·문헌 아이디어·코드 테스트만의 성공은
  발견으로 강조하지 않는다. 실험 무효·현재 결론을 막는 결함·리뷰 생략은 발견 알림에서 제외한다.
  유효한 제한적 관찰은 '관찰', 확증되지 않은 효과는 '불확정'이라고 명시하며 신규 contribution과
  구분한다. 관찰 요약에는 핵심 비교/수치와 적용 범위를 우선하고, 다음 검증을 한 줄로 덧붙인다.
- 결과와 마일스톤의 같은 내용을 두 번 보내지 않는다. 상세 마일스톤 story는 JOURNEY.md에,
  전체 문제 목록·수치·설정·실험 과정은 review.md에 남기고 Telegram에는 결과 알림 한 건으로 통합한다.
- 사용자 결정이 필요하면 질문·추천 이유·답장 방법을 분명히 한다. 필요한 권한·범위를 감추지 않는다.
  결정 요청은 일반 알림의 짧은 길이에 맞추려고 선택지 의미·승인 범위를 생략하지 않는다.
- 전체 계획이나 긴 오류 로그 대신 짧은 설명과 원문 위치를 보낸다. 표시 한도 때문에 축약하면 표시하고,
  중요한 결정을 하기 전에 원문을 확인하도록 안내한다. Telegram에서 Markdown 표에 의존하지 않는다.
- 불확정·실행 실패를 긍정적인 ‘완료’ 알림으로 오해하게 쓰지 않는다. 한 번의 반복 종료와 목표 완료를 구분한다.
- 연구 투자 보류를 알릴 때는 보류할 과제·조건과 이유를 명시한다. 검증 부족과 가치 부족을
  구분하고 중요한 관찰이 남으면 한 문장으로 적는다. 세부 수치는 원 리뷰에 둔다.

## 변경하지 않는 것

코드·알고리즘·실험 규모·metric·검증 기준·모델 등급·권한·자동 진행 조건은 이 문서 때문에 바꾸지 않는다.
JSON 필드명·enum·SELF_CHECK: PASS/FAIL·SUMMARY: 형식과 명령어는 그대로 유지한다.
추가 모델 호출로 문장을 다듬지 않는다. 표현 지침과 표시 템플릿만으로 적용한다.
