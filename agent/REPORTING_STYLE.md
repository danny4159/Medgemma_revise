# 사람이 읽는 기록·알림의 작성 기준

적용 대상: 계획 설명, 조사 노트, 구현 보고서, 리뷰, INDEX/DECISIONS/JOURNEY, 논문 추천, Telegram, 사용자 답변.
표현을 쉽게 만드는 기준이지 구현·연구·검증을 단순화하라는 지시가 아니다.

## 기본 순서

1. 핵심: 무엇을 하려는지 / 무엇이 확인됐는지 한두 문장으로 먼저 쓴다.
2. 근거: 판단에 필요한 수치·비교·출처를 제시한다.
3. 의미와 한계: 목표에 어떤 진전인지, 아직 무엇을 말할 수 없는지 구분한다.
4. 다음: 다음 작업과 이유, 사용자 결정이 필요한지 적는다.

- 짧은 문장에 한 가지 요점을 담는다. 장황한 작업 나열·반복 설명·전문용어 연결을 피한다.
- metric·모델명·기술 용어는 유지한다. 익숙하지 않을 용어는 처음에 짧게 뜻을 덧붙인다.
  예: data leakage(평가 정보가 학습·선택에 섞이는 문제), ablation(구성요소별 효과 비교).
- 숫자는 비교 대상·단위·표본 수와 함께 쓴다. 관찰, 해석, 추정을 구분하고 미실행·미검증을 명시한다.
- 코드 작성 완료, 테스트 통과, 유효한 실험, 가설 지지, 연구 목표 달성을 같은 ‘성공’으로 묶지 않는다.
- 제목·짧은 문단·목록으로 나누되 섹션을 불필요하게 늘리지 않는다. 표는 실제 비교가 쉬워질 때만 쓴다.
  Markdown 제목 뒤와 목록 앞에는 빈 줄을 둔다. 경로·명령·정확한 수치와 원문 링크는 유지한다.

## 요약과 상세의 분리

- 완성된 계획·구현 보고서·리뷰는 맨 앞에 ‘요약’을 둔다. 핵심/근거/주의/다음을 3~5개 짧은 항목으로 적는다.
  계획은 예정과 판단 기준, 구현은 실제 실행 결과, 리뷰는 판정과 근거를 중심으로 쓴다.
- 상세에는 기존 필수 섹션, 재현 명령·설정·파일·오류·검증 근거를 빠짐없이 남긴다.
  간결함을 이유로 필수 정보나 부정적 결과를 버리지 않는다. 원본 기록은 소급해서 다시 쓰지 않는다.
- 한 줄 요약(plan_summary, SUMMARY, one_line_summary)은 ‘무엇을 했고/할 것이며 무엇이 달라졌는지’가 드러나게 쓴다.
  보통 1~2문장으로 작성하고, 판단을 뒤집을 수 있는 조건·미검증 범위는 요약에도 남긴다.
- 조사 중에는 전체 계획 대신 ‘새로 확인한 것 / 의미 / 남은 질문과 필요한 확인’을 기록한다.
  research_notes의 근거·대안 비교·불확실성을 길이 제한으로 잘라내지 않는다.

## Telegram

- 모바일에서 읽기 쉽게 제목 → 핵심 결과 → 의미·주의 → 다음 행동 순으로 짧게 나눈다.
- 사용자 결정이 필요하면 질문·추천 이유·답장 방법을 분명히 한다. 필요한 권한·범위를 감추지 않는다.
- 전체 계획이나 긴 오류 로그 대신 짧은 설명과 원문 위치를 보낸다. 표시 한도 때문에 축약하면 표시하고,
  중요한 결정을 하기 전에 원문을 확인하도록 안내한다. Telegram에서 Markdown 표에 의존하지 않는다.
- 불확정·실행 실패를 긍정적인 ‘완료’ 알림으로 오해하게 쓰지 않는다. 한 번의 반복 종료와 목표 완료를 구분한다.

## 변경하지 않는 것

코드·알고리즘·실험 규모·metric·검증 기준·모델 등급·권한·자동 진행 조건은 이 문서 때문에 바꾸지 않는다.
JSON 필드명·enum·SELF_CHECK: PASS/FAIL·SUMMARY: 형식과 명령어는 그대로 유지한다.
추가 모델 호출로 문장을 다듬지 않는다. 표현 지침과 표시 템플릿만으로 적용한다.
